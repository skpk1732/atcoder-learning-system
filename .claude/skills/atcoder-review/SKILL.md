# AtCoder コードレビュー（複数エージェント）

ユーザー自身が書いた競技プログラミングのコード（主にPython/PyPy）を、**複数の視点を持つエージェントで並行レビュー**し、統合して返すスキル。単なる添削ではなく「なぜそうか」を教え、学習につなげる。

## 1. 入力の確定

レビュー対象のコードとコンテキストを集める:
- **最新提出モード**: 引数が `latest`／`最新`、またはユーザーが「最新の提出を」「AtCoderから取ってきて」と言ったら、
  `python 2_Areas/AtCoder/tools/fetch_submission.py`（AC限定なら `--ac`、1つ前なら `--index 1`）を実行する。
  - 出力JSONの `saved_to` のファイルを読んでレビュー対象にする。`problem_url`・`result`・`execution_time_ms` はコンテキストとして使う。
  - ユーザー名未設定エラーが出たら、AtCoderのユーザーIDを聞いて `2_Areas/AtCoder/tools/config.json` の `username` に保存してから再実行。
- **コード**: 引数が問題ID（例 `ABC085_C`）なら `2_Areas/AtCoder/精進記録/<ID>*.md` を読んでコード部を抽出。ファイルパスならそれを読む。どちらも無ければユーザーにコードを貼ってもらう。
- **問題コンテキスト**（TLE・計算量判定に必須）: 問題URL・**制約（N の上限など）**・何をする問題か。精進記録から取れなければ、1回だけまとめて質問する。
- **言語**: 既定は Python（PyPy提出前提）。違えば確認。

## 2. 複数エージェントで並行レビュー

**Workflow ツールで並行オーケストレーション**する（またはそれが使えない/コードが短い場合は Agent を並行で3つ呼ぶ）。各エージェントに同じコード＋コンテキストを渡し、**異なるレンズ**を割り当てる:

- **レンズ①：正確性・バグ・エッジケース**
  - ロジック誤り、off-by-one、1-indexed/0-indexed 混同。
  - 境界ケース: N=1・空・全要素同一・最大制約・負値・重複・0。
  - 出力形式: 改行/空白/小数の桁・端数、**数え上げの mod 取り忘れ**。
  - **各指摘には「具体的に失敗する入力例」を添える**。再現できない憶測は「要確認」と明示し、断定しない。

- **レンズ②：計算量・TLE・Python/PyPy高速化**
  - 時間計算量を O記法 で見積もり、**制約と照合**（[[計算量とオーダー]]）。間に合うか明言。
  - Python特有の遅い書き方: `input()` 未差し替え、`x in list`（O(N)）、`list.pop(0)`、文字列 `+=` 連結、深い再帰、1行ずつ大量 `print`（[[Python競プロTips]]）。
  - メモリ・PyPy向き/numpyが効くか。

- **レンズ③：簡略化・Pythonic・可読性**
  - 標準ライブラリ活用: `Counter`/`defaultdict`/`bisect`/`itertools`/`heapq`/`math`。
  - 内包表記・`zip`・`enumerate`・`sum`/`any`/`all` で短く。
  - 冗長な分岐・重複の削減。**ただし競プロ的に過剰な抽象化やdocstringは不要**（短く・正しく・速く、が価値基準）。

- **（任意）レンズ④：別解・典型**: より単純な典型解法やライブラリはないか。

## 3. 検証（重要）

統合前に、レンズ①が挙げた「バグ」を**採用前に妥当性チェック**する。具体的な失敗入力で再現できるものだけ「確定バグ」とし、怪しいものは「要確認」に格下げする。誤検知でユーザーを混乱させない。

## 4. 統合レポート

**重要度順**（① 確定バグ → ② TLE/計算量 → ③ 簡略化 → ④ 別解）でまとめる:
- 各項目: 「何が」「なぜ問題か」「どう直すか」を簡潔に。学習リンク（[[Python競プロTips]] / [[計算量とオーダー]] 等）を添える。
- **改善版コードを1つ提示**（正しさ最優先、その上で速度・簡潔さ）。元コードとの差分ポイントを一言。
- 良い点も1〜2個挙げる（何が正しくできていたか）。

## 5. 精進記録への反映

対応する精進記録ノートがあれば（または作成した直後なら）、**既存の「解答コード（要点）」節はそのまま残し**、末尾に以下の2節を追記する（ユーザー確認済みの標準形式）:
- 「## 実際の提出コード（日付・結果・実行時間）」— ユーザーの提出コードを原文のまま。提出ページへのリンクも。
- 「## コードレビュー（日付・3レンズ）」— 総合評価 → ①正確性 ②計算量 ③簡略化 → 良かった点 → レビュー反映版コード → レビューからの学び。
- レビューで判明した弱点は「学び」節にも1行足すと良い。
- 対応する精進記録が無い場合は、追記先を作るか（atcoder-record の手順で）聞く。

## 方針

- ユーザーの学習が目的。**直すだけでなく理由を教える**。競プロ文脈の判断基準（短く正しく速く）を守り、企業コード的な過剰リファクタは勧めない。
- **一時ファイルの置き場**: レビューエージェントが検証用スクリプト（stress test等）を作る場合は、必ずセッションのscratchpadディレクトリ（またはOSの一時フォルダ）に作らせ、ユーザーの作業フォルダ（vault）には何も残さないことをエージェントへの指示に明記する。終了時に消す。
- 断定できないバグは「要確認」と正直に。
